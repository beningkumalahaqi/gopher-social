# 30. Markdown as the content source

## Goal

Keep lessons as reviewable text files and still serve fast, safe HTML. This
lesson follows one file from embedding to the page.

## The source of truth

Lessons live in `docs-learn/` as Markdown. They are not generated into Go
strings, and the database does not store their bodies. The embed directive in
`docs-learn/embed.go` puts the directory into the binary:

```go
//go:embed *.md exercises/*.md solutions/*.md glossary.md examples/*/*.go
var files embed.FS
```

At startup, `learn.Load` globs `[0-9][0-9]-*.md`, renders each file once, and
keeps the result in memory. The filename is the slug. The two-digit prefix is
the lesson number. A new file appears in the curriculum on the next build with
no registry to edit.

This is why lesson pages are fast: no file read, no Markdown parse, and no
database query for the body on the request path.

## Rendering is a pipeline

`NewRenderer` configures Goldmark with GFM, footnotes, and Chroma syntax
highlighting. It also registers a link transformer that rewrites relative links:

```go
if strings.HasPrefix(dest, "docs-learn/") || strings.HasPrefix(dest, "../") {
    // Resolve to a learning URL when the target is a doc, otherwise RepoURL.
}
```

After rendering, Bluemonday sanitizes the HTML with a policy that allows the
markup the curriculum actually uses. Code spans keep only `class` values that
match a safe pattern. Unknown elements and attributes are dropped. The result
is assigned `template.HTML`, which tells `html/template` that trust has already
been established.

Order matters: transform links, render Markdown, sanitize, then mark trusted.
Sanitizing before rendering would miss markup generated by the renderer.
Trusting before sanitizing would defeat the whole pipeline.

## Metadata comes from the document

One parse produces more than HTML:

```go
type Parsed struct {
    Title   string
    HTML    template.HTML
    TOC     []Heading
    Text    string
    Code    []string
    Words   int
    Summary string
}
```

- `Title` is the first H1, with the number prefix stripped.
- `TOC` is built from H2 and H3 nodes. The layout renders it as a rail on wide
  screens and a disclosure on narrow ones.
- `Text` is the plain text used by search and reading time.
- `Code` is every code block, indexed separately so a search for `sqlc` can
  match code even when the prose does not mention it.
- `Summary` is the first paragraph, used in cards and meta descriptions.

Deriving all of this from the file prevents the metadata from drifting from the
content. There is no front matter to forget and no second title to update.

## Heading IDs and deep links

`parser.WithAutoHeadingID` gives every heading a stable id derived from its
text. The TOC links to those ids, and browsers keep the fragment when the page
loads. Two lessons with the same heading text in different files do not collide
because ids are scoped to a document.

If you rename a heading, its id changes and existing deep links break. Treat
heading text as part of the public URL once a lesson is published. Add a new
heading instead of rewriting a linked one when possible.

## Code highlighting without a client library

Chroma runs on the server and emits classes, not inline styles. The CSS owns
the palette, so light and dark themes both work without shipping a highlighter
to the browser. The `pre` element also gets a copy button from `learn.js`.
Copying is progressive enhancement; selecting the text still works without it.

Server-side highlighting does add startup work proportional to the corpus. At
this size it is measured in milliseconds. If the corpus grew by an order of
magnitude, render in a build step and embed the HTML. Do not add client-side
highlighting to avoid a problem you have not measured.

## Failure modes

A malformed file does not crash the process. `loadDoc` returns a diagnostic and
the loader continues:

```go
doc, diag := loadDoc(fsys, renderer, name, KindLesson)
if diag != nil {
    c.Diagnostics = append(c.Diagnostics, *diag)
    continue
}
```

Diagnostics are logged at startup and shown on the dashboard in development.
A missing module range, an unknown activity lesson slug, or a duplicate lesson
number is visible before a user finds it. The build still succeeds, because one
bad lesson should not take down the platform.

The trade is that a diagnostic can be ignored. Treat a new diagnostic in the
startup log as a failing test, even though the process is healthy.

## Exercises

1. Add a fenced code block with an unknown language and see how Chroma and the
   sanitizer handle it.
2. Rename a heading, reload, and observe the TOC id change.
3. Write a lesson with a `<script>` tag in the Markdown and confirm it is
   removed by the sanitizer.

## What to remember

Embed the corpus, parse once at startup, transform then sanitize then trust,
derive metadata from the document, and surface diagnostics instead of hiding
them.
